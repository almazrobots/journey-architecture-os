# Evaluations

The `evals/` suite checks two things that validation alone cannot: whether an agent picks the right skill, and whether loading a skill makes its output better.

- **Routing** (`evals/routing.jsonl`, 111 cases: 24 easy, 87 hard; every one of the 15 skills has at least 5 hard cases, which `--check` enforces). The model sees each skill only as the `name` and `description` from its `SKILL.md` frontmatter, the way an agent client sees them before loading one, and picks one skill or `none`. The 15 skills are listed alongside 14 fictional neighbour skills from `evals/distractors.json`, in the same format: process mapping (BPMN), user research, persona creation, survey design, generic workshop facilitation, KPI dashboards, incident postmortems, IT service desks, and others. The order of the listing is shuffled per case with a fixed seed to control position bias, and the seed is recorded. Cases cover a clear request for each skill; broad requests that belong to `experience-architecture`; near-misses (prioritize vs. design the future, EJM for a manager vs. CJM for a customer who is a manager); intent with no method vocabulary; misleading keywords ("map the onboarding process" in BPMN, "hero's journey", "plan my journey to Japan"); requests where a neighbour skill is the right tool (an outage postmortem, NPS survey wording, marketing personas, a team retrospective); multi-step requests where the first skill matters; out-of-scope requests that must route to `none`; and requests in Russian, German and Spanish. 19 cases are tagged `"heldout": true`. They are kept out of description tuning: nobody may use them to adjust a skill description. Their accuracy is reported separately and is the honest estimate. The report gives exact-primary and acceptable accuracy, overall, by difficulty, and for held-out vs development cases. It also lists non-exact cases in two groups, misses and acceptable-but-not-exact, plus per-skill misroutes, *distractor steals* (one of our skills was expected but a neighbour was picked) and *over-triggers* (one of our skills was picked for a case that is not ours). `--no-distractors` runs the older, easier condition with only the 15 skills. There, a case whose right tool is a neighbour expects `none`.
- **Behavior** (`evals/behavior/*.json`, 8 scenarios, one each for research, CJM, EJM, blueprinting, moments that matter, metrics, prioritization and audit). Each scenario gives a request phrased the way a real user writes it, with no method vocabulary and no list of expected sections, plus compact fictional input material. The material contains 3 to 5 subtle traps that only a skill's method or quality gates would catch: interviewees recruited only from people who completed, qualitative counts that invite percentages, stages derived from departments or screens, an agency summary with no sample, an operational metric that improves while the actor outcome worsens, an average that hides a segment split, ticket volume read as prevalence, a root cause that stops at "human error", a single 5-whys chain where causes combine, roadmap features written into current-state notes, NPS used as a stage metric, a ratio whose denominator changed, and solution directions worded as opportunities. The scenario's `notes` field lists the traps for maintainers and is never sent to the model or the judge. Each scenario runs with the skill loaded (its `SKILL.md` plus the files it references, read from disk at run time) and without it, `--repeats N` times each. Regex assertions check `convention` properties locally, such as IDs matching the ontology grammar. The placeholders `@ontology-id-finder` and `@ontology-id-grammar` are resolved at run time from the regular-expression block in `skills/journey-architecture/references/ontology.md`, so the ontology is the only list of ID prefixes (including `CHG`) and eval files never copy it. Most assertions are `method` judge questions about one specific trap, with explicit pass criteria. A separate model call grades them without knowing which condition produced the answer, and generic caution that does not name the specific trap fails. Before a `method` judge sees an output, the runner normalizes it to remove tells about the condition: ontology IDs, with prefixes taken from the ontology, become consistent placeholders (`[ID-1]`, `[ID-2]`, ...) and the suite's skill names become `[SKILL]`. Regex assertions and the stored raw outputs are unchanged. Judge questions test the reasoning, not a preferred answer: where an item could reasonably go either way, as with a low-reach but high-consequence moment, the question asks whether the trade-off was weighed. The report shows mean pass rates for each condition, pass counts per assertion (k/N), and the with-vs-without difference with a 95% bootstrap CI (resampling scenarios, fixed seed) and an exact sign test over assertions. `convention` results favour the with-skill run by design, so `method` is reported separately and is the measure that matters.

Run:

```bash
python3 scripts/run_evals.py --check                      # validate eval files, no model calls (runs in tests)
python3 scripts/run_evals.py --mode routing --dry-run --limit 1   # print a prompt (with its shuffle seed), no model calls
python3 scripts/run_evals.py --mode routing                  # with distractors (default)
python3 scripts/run_evals.py --mode routing --no-distractors  # only the 15 skills
python3 scripts/run_evals.py --mode behavior --repeats 3        # full behavior suite, 3 runs per condition
python3 scripts/run_evals.py --mode behavior --case BH-02-cjm-move-home
python3 scripts/run_evals.py --mode behavior --cmd "your-agent-cli --print" --model some-model
```

The model is reached through any shell command that reads a prompt on stdin and prints the answer (`--cmd`). The default is Claude Code in print mode, isolated as far as its CLI allows: `claude -p --safe-mode --setting-sources '' --strict-mcp-config --disable-slash-commands --tools '' --no-session-persistence --system-prompt '<neutral prompt>'`, run from an empty temporary directory that is deleted after the run. This means no CLAUDE.md or project memory, no user or project settings, no hooks, plugins, MCP servers, skills or built-in tools, and no saved session. `--model` is appended as `--model <name>`, or substituted for a `{model}` placeholder in a custom `--cmd`. Other options: `--repeats` (behavior runs per condition, default 1), `--allow-dirty`, `--seed` (base seed for the routing shuffle, default 0), `--jobs` (default 3), `--timeout`, `--retries` (malformed JSON, default 2), `--limit`, `--case`. Results are written to `evals/results/<YYYY-MM-DDTHHMM>-<kind>[-rN][-limitN][-caseN].json` (raw, including outputs and judge reasons) and `.md` (summary). `<kind>` is `routing`, `routing-no-distractors` or `behavior`; `-rN` is the repeat count, and the other suffixes record filters. Existing files are never overwritten: a clash gets `-2`, `-3` and so on. Results are meant to be committed.

**Results integrity.** Each result records the full `git rev-parse HEAD`, a dirty flag with the changed files (`evals/results/` itself is ignored), and the sha256 of every file loaded into the prompts: each `SKILL.md`, every reference file a skill pulls in, and the eval files. The runner refuses to write into `evals/results/` from a dirty working tree, and checks this before making any model calls. `--allow-dirty` overrides the refusal; such results are marked `DIRTY - not a release result`. Writing to another folder with `--results-dir` is allowed, but a dirty run is still marked. A result is a **release** (`"release": true`) only when the tree was clean and no `--case` or `--limit` filter was used; filtered runs are marked `Partial run - not a release result`. `evals/results/latest.json` points to the newest release result of each kind, with its commit, and only release runs update it.

**Cost.** Routing makes one call per case. Behavior makes, per repeat, 2 generation calls per scenario plus one judge call per judge assertion per condition: about 76 calls per repeat, so about 230 for `--repeats 3`. Use `--limit` and `--case` while iterating.

**Adding a case.** Append a line to `routing.jsonl` (`id`, `difficulty` of `easy` or `hard`, optional `heldout`, which marks a case that must never be used for tuning, `prompt`, `expected` with one skill, a distractor name or `none`, `acceptable`, `notes`), or add a `behavior/<ID>.json` file with `id`, `skill`, `prompt`, `input_material`, `assertions` and an optional `notes` field listing the traps. Write the prompt as a user would, without method words, and make each judge question name one specific trap. Each assertion has an `id`, a `type` (`regex` or `judge`) and a `category` (`convention` or `method`). A regex assertion takes `pattern` or `all_of`, with optional `every_match`, `flags`, `min_count` and `negate`. A judge assertion takes `question` and `pass_criteria`. Never paste skill text into eval files. Run `--check` before committing.

**Limits.** With 8 scenarios the bootstrap CI is wide; a CI that includes 0 means "not shown", not "no effect". Routing runs each case once. The judge is the same model family as the model under test. Routing is measured from descriptions only, not from a real client's skill loader, and the distractors are one fixed, fictional neighbourhood.

Latest results: see `evals/results/` (`latest.json` names the current release result for each kind).
